# 단기기억과 장기기억 — 설계 개정판

> 원본 문서의 뼈대를 유지하고, 비어 있던 네 지점을 채운 개정판.
> **채운 것**: ① 엔티티 해소 규칙 ② 모순/갱신(supersede) 정책 ③ 단기기억 compaction ④ 벡터 진입점.
> 표기: `▲개정` = 이번에 추가/보강된 부분.

---

## 0. 원칙

- 장기기억과 단기기억의 **저장 장소를 분리**한다.
- API 호출에 **2개 키**를 추가로 받아 장기/단기 접근을 나눈다.
  - **U_ID** — 개인화 ID. 장기기억 접근에 관여.
  - **S_ID** — 세션 ID. 동일 세션은 동일 단기기억에 관여.
- (선택) **API 키** 단위로 도메인 기초지식·개인화 정책을 얹는다. → 테넌트 계층.

## 1. 저장소 구성

| 계층 | 저장소 | 담는 것 | 키 |
|---|---|---|---|
| 작업기억(단기) | **Redis** | 현재 세션 원문 + 롤링 요약 | S_ID |
| 장기기억·구조 | **GraphDB** (우선 Postgres+AGE로 시작 가능) | 엔티티, 관계, 노드 키, 가중치, 호출횟수, 시점 | U_ID |
| 장기기억·내용 | **RDB (+pgvector)** | 사실 원문, 원시데이터, 임베딩 | U_ID |
| 테넌트(선택) | RDB | 도메인 기초지식, 개인화 정책 | API 키 |

> `▲개정` **벡터(임베딩)는 GraphDB가 아니라 RDB(pgvector)에** 둔다. GraphDB는 탐색 인덱스로 가볍게 유지.
> `▲개정` GraphDB는 물리적으로 나중에 분리한다. **우선 Postgres 단일(+AGE 확장 또는 재귀 CTE)로 시작** — 1인 운영에서 이중 저장소 세금을 뒤로 미룸.

## 2. 기억의 저장 (쓰기)

### 2.1 장기기억 저장 — "특정 방식" 상세

원시 로그와 기억을 **분리**한다.

1. **원시 로그(항상, 인라인)**: 모든 호출의 질문/답변을 RDB에 append. 감사·재현·재추출용.
2. **기억 추출(비동기)**: 응답 후 큐로 처리. 매 답변이 추출을 기다리지 않게 한다.

추출 산출물: **엔티티 / 관계(트리플) / 사실 / 가중치 / 시점 / 원시키**.

예시 — "나 하람아이 다니고 노드로 백엔드 개발해. 다음주 부산 출장 가."

| 주어 | 관계 | 목적어 | 부가내용 |
|---|---|---|---|
| 사용자 | 소속 | 하람아이 | |
| 사용자 | 사용기술 | 노드 | |
| 사용자 | 직무 | 백엔드개발 | |
| 사용자 | 예정일정 | 출장 | 장소=부산, 시점=다음주 |

- GraphDB: 위 엔티티/관계/가중치/호출횟수/시점 + 각 트리플의 **원시키**.
- RDB: 사실 원문, 원시데이터, 임베딩.

#### 2.1.1 `▲개정` 엔티티 해소 (Entity Resolution) — 핵심

"하람아이"(1턴)와 "우리 회사"(50턴)를 **한 노드**로 모으는 규칙. 없으면 중복 노드로 쪼개져 **호출횟수·가중치가 분산되어 무너진다.**

해소 순서(위에서부터 먼저 성공하면 채택):

1. **정규화**: 소문자화·공백/문장부호 정리·별칭 사전 치환("(주)하람아이"→"하람아이").
2. **표면형 정확 일치**: 정규화된 이름이 기존 노드와 같으면 그 노드.
3. **별칭/약어 사전**: 사전에 매핑된 동의어면 그 노드.
4. **임베딩 유사도**: 엔티티 설명 임베딩이 기존 노드와 pgvector 유사도 **임계값 이상**이면 같은 노드(다국어·표기차 흡수).
5. **대명사·지시어 해소**: "우리 회사", "거기", "그 사람"은 먼저 **세션 컨텍스트(Redis)** 로 실제 엔티티를 찾아 **치환한 뒤** 저장한다. (해소 실패 시 저장하지 않음)
6. **애매하면**: 새 노드를 만들되 **낮은 신뢰도 + 병합 후보 링크**를 달아, 이후 재확인 시 병합할 여지를 남긴다.

> 원칙: **표기·언어·대명사를 하나의 정규 엔티티로 수렴**시키는 것이 "특정 방식"의 심장.

#### 2.1.2 `▲개정` 가중치 함수

가중치를 **호출횟수만으로 정하지 않는다**(사소하지만 자주 나온 것이 드물지만 중요한 것을 이기면 안 됨).

```
weight = w_count · log(1 + 호출횟수)
       + w_recency · decay(now - 최근시점)     // 오래되면 감쇠
       + w_explicit · 명시성                    // 직접 진술 > 추론
       + w_type · 중요도(관계타입)              // 건강/신원 등 > 잡담
```

- 파라미터 `w_*`는 튜닝 대상.
- 일회성 오추출은 호출횟수·명시성이 낮아 **자연히 약하게** 남고, 반복 확인되면 강해진다(승격).

#### 2.1.3 `▲개정` 모순 / 갱신(supersede) 정책

같은 `(주어, 관계)`에 **새 목적어**가 오면 잠재 모순. 처리는 **관계의 cardinality**로 결정:

- **단일값 관계**(소속·거주지처럼 "1개만 참"): 옛 엣지에 `valid_to = now`를 찍어 **히스토리로 남기고**, 새 엣지를 `valid_from = now`로 추가. (삭제하지 않음 → "예전엔 하람아이였다"도 회상 가능)
- **다중값 관계**(사용기술·관심사): 병렬로 추가(모순 아님), 각자 가중치.
- 관계 온톨로지에 **cardinality(단일/다중)** 를 정의해 이 분기를 자동화.
- 오래 미참조된 엣지는 가중치 감쇠로 자연 후순위화(soft-forget).

### 2.2 단기기억 저장 (Redis)

- 이번 S_ID로 받은 내용을 Redis에 저장. 관계도보다 **원시데이터 기준**으로 저장해도 됨.
- `▲개정` **compaction (무한 팽창 방지)**: 세션이 길어지면 프롬프트가 커져 느려진다. 따라서 작업기억 = **최근 N턴 원문 + 롤링 요약**으로 바운드.
  - 토큰 예산 초과 시 오래된 턴을 **요약에 접고**(증분·비동기 요약), 원문은 버린다.
  - 접힌 내용의 durable 사실은 어차피 §2.1 장기 추출로 소화되므로 **손실 없음**.
- `▲개정` **슬라이딩 TTL**: 매 턴마다 TTL 리셋 → 대화 중간에 세션 만료 방지.

## 3. 기억의 검색 (읽기)

### 3.1 진입점 — 두 갈래로 노드 키를 찾는다

- **(A) 정확 지칭**: 라우터가 뽑은 엔티티/키워드 → 엔티티 링킹 → GraphDB 노드로 직행.
- **(B) `▲개정` 흐릿한 표현**: 질문 임베딩 → **RDB(pgvector) 유사도 검색 → top-K seed 노드 키**.
- 두 경로 모두 결국 **"노드 키"로 수렴** → 다음 단계로.

> 요지 파악은 **이미 있는 라우터 기능을 재사용**(읽기측·인라인·저비용). 무거운 추출은 쓰기측(§2.1)에서 비동기로.

### 3.2 그래프 확장 (뻗어나가기)

- seed 노드에서 **가중치·최신성 높은 엣지로 1~2홉만, top-N 바운드** 확장. (블라인드 BFS 금지)

### 3.3 원문 fetch + rerank

- 확장된 노드/엣지의 **키로 RDB에서 원문**을 가져온다.
- `▲개정` **rerank**: `벡터유사도 + 가중치 + 최신성 + 중요도`로 재정렬 → 상위 N만 채택.
- `▲개정` **임계값 가드**: seed 최고 유사도가 낮으면(=관련 기억 없음) **억지로 넣지 않고** 기억 없이 답한다. (엉뚱한 회상으로 자신 있게 틀리는 것 방지)

### 3.4 작업기억으로 전환

- 회상 결과 + 최근 세션을 병합해 프롬프트 구성.
- 이후 **같은 S_ID** 요청은 Redis에서 바로 꺼내 쓴다(핫). 새 S_ID면 장기기억에서 다시 하이드레이션.

### 3.5 단기기억 검색

- **Redis** 사용. S_ID로 조회.
  - 활성 → 그대로 사용.
  - 비활성/첫 대화 → 새 세션 생성 + U_ID 장기기억에서 **최근·핵심만 바운드 하이드레이션**.

## 4. 요청 1회 처리 흐름 (읽기 → 답변 → 쓰기)

1. **수신** (U_ID, S_ID, 질문)
2. **작업기억 조회**(Redis, S_ID): 활성=핫 사용 / 비활성=새 세션 생성 + 장기기억 바운드 하이드레이션
3. **진입점 탐색**(§3.1): 엔티티 링킹(정확) + pgvector(흐릿) → seed 노드 키
4. **그래프 확장**(§3.2) → **RDB 원문 fetch + rerank**(§3.3), 임계값 미달이면 회상 생략
5. **답변**: (작업기억 + 회상 + 도메인지식) 병합 컨텍스트로 생성
6. **되쓰기(두 속도)**:
   - Redis에 이번 턴 **즉시 append**(필요 시 compaction)
   - RDB 원시 로그 append + **비동기 추출→GraphDB/RDB 반영**(엔티티 해소·가중치·모순 정책 적용)

## 5. 결정이 필요한 항목

- **GraphDB 물리 분리 시점**: 우선 Postgres(+AGE) 단일, 탐색이 실제 병목임이 증명되면 Neo4j 분리.
- **관계 온톨로지**: 엣지 타입을 고정 스키마로 둘지/자유형으로 둘지 + 각 타입의 cardinality(단일/다중).
- **가중치 파라미터** `w_*`와 감쇠 함수 튜닝.
- **임베딩 모델**: 다국어 회상을 위해 다국어 임베딩 선정(풀의 `embedding` 역할 재사용).
- **개인정보**: 장기 개인기억 = 개인정보 장기 적재. 삭제/열람/동의(개인정보보호법)를 데이터모델에 처음부터 반영.
